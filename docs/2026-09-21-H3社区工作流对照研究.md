# MiniMax H3 社区工作流对照与改进建议

核查日期：2026-09-21。项目基线：`a8fc512`（包含本轮随机种子回调修复）。

## 结论与证据边界

当前工作流可以改进，优先顺序应是：修复执行与控件缺陷 → 建立干净基线 → 验证一采与二采音频 → 改善身份参考与局部修复 → 单独测试新的加速器。

本轮检索 GitHub 公开仓库、官方链接和案例索引，读取 24 个项目的 README，深入核对官方模板、官方问题讨论，以及 AIMixer、T8、LBH 的部分实现。不能声称覆盖“全网所有工作流”：付费、登录可见、未发布 JSON 的教程未逐一核验；本次通用搜索页返回了 JavaScript 验证页，核心结论采用可直接读取的源仓库。以前提到的 U27/U28 本地下载文件本轮未找到，不推断它们当前的具体参数。

证据分为：

- **源码/JSON 可核实**：字段、接线、默认值、音频回填、模型选择和分块实现。
- **作者实测**：来自维护者报告，仅适用于其硬件、模型、素材和长度，没有当作本项目实测。
- **本项目回归测试**：验证代码行为和图结构，不能证明视频更清晰或音色更像。
- **仍待 GPU 对照**：本轮没有新跑生成基准，没有自动安装社区插件/权重，没有修改 ComfyUI 核心或提示词技能。

## 本轮确认并修复的问题

| 问题 | 影响 | 修复与验证 |
|---|---|---|
| 原生种子回调丢失 `this` | 入队后的随机/递增种子更新报 `Cannot read properties of undefined (reading 'options')`；不等于后台任务未提交 | 包装回调保留接收对象、完整参数与返回值；测试先复现相同异常再通过；提交 `a8fc512` |
| “16（最省显存）”只提取首位数字 | 手动 16 被解析成 1；后续档位校验会忽略它并回退自动/预设，未真正采用手动 16 | 解析完整数字，覆盖自动、2、4、8、16 全部档位 |
| 主图跟踪预览是独立输出根节点 | 最终懒加载开关关闭时，活动 `PreviewImage` 仍能请求跟踪分支、加载检测模型 | 主图预览设为 Never；最终修复路径仍可由统一开关启用；独立 tracking-only 示例保留预览。增加图结构与重复整合测试 |

第二、三项修复后的完整回归结果：936 passed。此前关于“关闭时完全不执行检测”的结论遗漏了独立预览输出，应以此处为准。

## 对我们最有价值的改进

### 1. 先建立不叠加社区风格 LoRA 的基线

`nodes/performance.py` 的 `MiniMaxH3AccelerationRouter` 和 `_apply_optional_detail_loras` 默认是“全部自动叠加”。只要本地安装对应文件，双阶段就可能叠加武术物理、Mystic、动作连续性、电影质感等多种 LoRA；它们不是 MiniMax 官方通用质量保证。同一 JSON 在模型目录不同的机器上可能得到不同的有效模型。

官方模板有自己的基础/加速选择，不能把“官方模板中出现 Turbo 节点”理解为“所有模式都必须叠同一 Turbo”。本轮下载的 R2V 模板包含 `res_multistep`、`simple`、20 步和可切换的 Ref Turbo；T2V 模板另有采样与 LoRA 配置，应按实际激活分支读取。

**建议**：用现有“全部关闭”选项制作固定种子对照，保留需要的训练型两阶段 LoRA，只关闭额外社区 LoRA。确认人脸、姿态、声音和耗时后，再决定是否把清洁基线作为默认。不能断言当前质量问题全由 LoRA 引起；本轮不擅自改变这些生成默认值。

### 2. 768p 是输出尺寸，必须同时展示真实生成尺寸

本轮运行日志显示一条低显存 10 秒 T2VA 路线的一采是 **512×288**，目标是 **1344×768**；后续有 latent 二采与像素超分。它不是原生 768p，最终文件尺寸不代表起始脸部细节足够。

LBH 明确说明：学习型 latent 放大主要省去 VAE 解码→像素放大→重新编码的开销，**单靠放大网络不会免除高分辨率二采的峰值显存**。时空分块是另外一层机制，会引入上下文与接缝权衡。我们已经使用其 Split Upscale、重叠、锚点与有限 OOM 重试，并非需要再并排增加另一套相同节点。

**建议**：导演台展示“首采尺寸 → 二采尺寸 → 最终尺寸”、实际步数、分块数和生效 LoRA。把“允许运行”与“已通过清晰度实测”分开。8GB 768p 10 秒作为明确验收目标，不把兼容的 15 秒低网格路线表述为相同画质。

### 3. 音频问题分成声纹、生成噪声、后处理三层处理

官方仓库 issue #17 仍为 open；内容与评论来自社区用户，不是官方承诺已有解决方案。报告涉及两人轮流对白串色；有个案通过移除未标记的轻笑改善，但不是稳定通用修复。

官方 Ref2VA 规则确认 `(Sx)` 按目标视频首次实际发声顺序分配，和 `<Audio N>`、`<Subject N>` 是不同编号。本项目已存在相应检查，不应重新强制同号绑定。

本项目 `nodes/two_stage.py` 已在第二阶段结束后回填一采音频 latent；低显存参考路线另外使用零音频噪声/遮罩保护。这能防止二采交付音频漂移，**不能修复一采就生成错误的声纹或杂音**。

T8 H16-3 同样默认 `preserve_first_pass`，二采音频 `refined_exp` 是实验选项。其公布的资格样片只有 73 帧、416×224→832×448，不能当作三人 15 秒已解决。SelfLift Avatar 也要求视频全生成/音频全保留的特定遮罩，并给空间块完整音频条件；这是采样约束，不是声纹克隆保证。

此外，本项目“自动音频响度”实际还包含门限/频谱降噪，`original` 才旁路波形清理。频谱处理可能压低辅音或改变质感，不能只凭音量正常判断质量。

**建议验证**：保存一采原始 WAV、二采解码 WAV、最终自动处理 WAV，使用相同输入比较；先证明杂音在哪一阶段出现，再决定改采样还是降噪。后续将“响度”与“降噪”分成清楚的独立选项。严格角色声音任务可增加“已生成对白音轨驱动画面”的明确模式，但不能把已有 Fish 参考模式宣称为无条件严格锁声纹。

### 4. 人脸修复需要身份入口，不能仅依靠“右侧人物”

当前主图的真实配置：`right_most`、`identity_track=False`、`cut_detection=none`、没有外接 `identity_reference`，修复参考来自生成视频的首个裁剪帧。它并不是自动识别所有角色；如果原片的脸已经错了，再参考这张脸重绘，可能保留错误身份。

Carasibana 最新上游 commit `d8521d14fe0d721d80cd9417fff5a559cbc21aba` 与我们内置来源一致。本轮没有找到“更新上游即可解决”的依据。其支持按镜头选人、身份参考、切镜检测、缺席镜头跳过和可选遮罩；但项目包装节点和主图只使用了其中一部分。位置排序不能替代身份匹配。

T8 FaceRefine Window 更值得借鉴的是“局部时间窗候选→检查→接受/拒绝→原音轨合成”的流程，仍标记 Advanced EXP，公开矩阵是 16GB，不是 8GB 保证。

**建议设计**：保留统一开关；增加修复目标（角色/明确选脸）与对应原始清晰参考，按切镜分段，遮挡或目标不在镜头时跳过；低显存按短窗口串行处理。先交付原片与候选对照，效果未经验证时继续默认关闭。人脸方案不负责修正猫狗身体比例、站位和场景几何；人脸检测器也不能自动当作猫狗身份识别器。

### 5. 新加速方案按路线单独试，不叠满

| 方案 | 可借鉴的点 | 证据与采用边界 |
|---|---|---|
| 官方 LightX2V / Larry Turbo v4 | 少步数、路线专用适配 | Larry 建议 v4 6–8 步改善高速运动拖影，并承认音频仍是弱项；其 `low_vram` 合并策略在量化底模上可能更软。不能把不同 Turbo 的步数/强度混用 |
| FastH3 dense LoRA 转换 | 候选 6 步快速路线 | NikoDemon80 报告 3070 Ti 8GB、48GB RAM、768×1344/124 帧约 6分30秒，20步约18分钟；属于作者主观质量比较，只验证到约5秒。AdaLN/权重融合转换有条件，不能直接替换我们的 hybrid 配方 |
| SelfLift / SelfLift Avatar | 低分辨率前缀、latent lift、高清后缀，减少高分辨率采样调用 | AIMixer 有独立 SelfLift 入口；Avatar 明确实验性且支持有限遮罩/分块。与当前二采属于替代候选，先单独 A/B，不默认层叠 |
| 分头注意力与 MLP 分块 | 降低临时显存峰值，避免直接牺牲空间网格 | 我们已有类似机制。T8 固定样本的显存收益只有约2.06%、耗时增加2.92%，不能声称必然省一半显存；必须看真实覆盖和开销 |
| comfy-kitchen INT8 attention | 高显存新卡可测，保持基础采样配方 | 独立作者在5090/4090上报告收益；不同GPU、dtype和Core版本有边界。不能把5090结果直接套3070 |
| Spectrum / BlockCache | 减少完整模型计算次数 | Spectrum 维护者明确写过音频混合引入 speech/stutter 回归，现有复杂保护不能当作无损；多角色对白先不默认启用 |
| VDN / OpenVDN | 新注意力架构，长序列候选 | 消费级 PyTorch port 明确不推荐显存/内存受限用户；官方集群倍数不能外推8GB。高显存单独实验 |
| Motion Context | 长片直接续接尾部 latent 和音频上下文，减少反复编码 | 适合长片扩展；不是“单个15秒镜头内身份与站位必然稳定”的解决方案，且需要核对Core版本 |
| RefMod | 参考资产压缩/复用 | 上游明确 under construction，音色迁移当前测试失败；不作为我们声纹修复方案 |

### 6. 建立官方可复现对照，而不是继续只比提示词

同提示词不等于同工作流：底模（官方 Ref/FL 或 hybrid）、文本编码器、图片预处理、尺寸、步数、sigma/sampler、LoRA、attention、参考素材顺序、输出降噪/超分都可能改变结果。

官方 H3 README 说明本地 Base 对应 768p，完整官方 2K 系统另含 Context-IR 与 Regenerate-2K API。社区二采/SeedVR2 不等同于官方未完整开源的端到端 2K 系统，不能拿官网2K宣传结果作为本地8GB必然可达到的基线。

## 建议执行次序与验收矩阵

保持现有已知可跑路线。新增方案先作为候选，不静默替换用户保存的配置。每组比较至少使用3个固定种子、同一素材和相同模型版本；一组A/B保持同seed，跨组换seed，并排除完整缓存命中。正在运行的用户任务不打断。

| 目标 | 对照顺序 | 验收内容 |
|---|---|---|
| 8GB，1080p，4–5秒 | 当前二采 → 关闭额外社区LoRA → 单独快速候选 | 实际采样尺寸、峰值显存/RAM、总耗时、脸部/手/细纹、帧间闪烁、音轨 |
| 8GB，768p，10秒 | 当前路线 → 同网格清洁基线 → 更高首采网格+分块候选 | 不以输出尺寸代替细节；检查近景与远景、分块接缝、切镜人物比例 |
| 24/32GB，1080p，15秒 | 官方/当前原生参考基线 → 无额外LoRA二采 → FastH3或SelfLift二选一 | 单人/三人对白分开；听辨声线、台词正确率、口型、跨镜身份与稳定性 |
| 人脸局部修复 | 原片 → 按身份选人短窗 → 合成候选 | 引用原角色参考；逐镜核对未串人、未软化、嘴型与原音轨时序未破坏 |

样片应包括：单人小脸、三人对白、一次切镜、快速动作。人脸相似度仅辅助真人角色，不能用人类 ArcFace 指标判定拟人猫狗质量。噪声听测必须响度匹配，避免把更响误判为更清晰。
