# 官方 LightX2V LoRA 加载修复设计

## 问题

当前 `_load_lightx2v_lora()` 优先调用 `ComfyUI-MiniMax-H3-Turbo` 的专用加载器，但服务器日志已经证明：官方 LightX2V 权重虽然被找到，实际结果却是 `0 adapters / 0 injections`，前向检查仍为 `BASE ONLY`。导演台随后仍按低步数加速路线采样，导致画面细节涂抹、颗粒和结构异常。

## 修改范围

- 官方 LightX2V FL2V、REF2V LoRA 统一改用 ComfyUI 内置 `LoraLoaderModelOnly`。
- 保留现有的嵌套模型路径解析能力，兼容模型位于 `models/loras/minimax/` 等子目录的情况。
- 加载前后统计 `ModelPatcher.patches` 中的补丁条目总数；只有新增补丁数严格大于零，才判定 LoRA 真正生效。
- 成功时记录中文日志，包括 LoRA 名称、强度和新增补丁数。
- 加载异常或新增补丁数为零时，在采样开始前给出明确的中文错误并终止本次生成，不能静默进入低步数基础模型路线，也不能显示“加速已启用”。

本次明确不修改：LoRA 强度、采样器、调度器、Sigma、步数拆分、二采放大倍率、RTX VSR、工作流连线、导演台界面布局和 API 入参。

## 数据流

```text
原始 ModelPatcher
  → 解析已注册的官方 LoRA 路径
  → ComfyUI 内置 LoraLoaderModelOnly
  → 比较加载前后的补丁条目总数
  → 新增补丁数 > 0：交给现有一采/二采模型路由
  → 新增补丁数 = 0：采样前终止并报告兼容错误
```

使用补丁条目总数而不是补丁键数量，是为了兼容同一模型键叠加多个 LoRA 的情况。

## 错误处理

- 找不到模型文件：沿用现有中文缺失模型提示。
- ComfyUI 内置加载器报错：包装为包含 LoRA 名称的中文兼容错误。
- 加载器返回模型但没有新增任何补丁：视为加载失败，立即停止任务。
- 不再为官方 LightX2V 权重调用 Larryvrh Turbo 系列的自定义注入器。

## 兼容性

- 导演台模式、性能模式、分辨率和最终输出选项保持原样。
- 工作流无需重新连线，API 字段不变。
- 仅改变官方加速 LoRA 的内部加载契约和失败判定。

## 测试与验收

- 验证嵌套路径解析后的 LoRA 名称和强度被传给内置加载器。
- 验证新增补丁条目大于零时加载成功。
- 验证新增补丁条目为零时抛出清晰错误，且不调用旧的专用注入器。
- 验证加载器自身异常不会被伪装成“加速已启用”。
- 运行性能路由相关测试、全量测试、Python 编译检查和 Git 差异检查。
- 不启动本地 ComfyUI；服务器实机验收时，日志必须出现正数的新增补丁数，不能再出现 `0 injections` 后继续低步数采样。
