# MiniMax H3 训练型 Latent 二采与安全高分辨率输出设计

## 目标

替换 U11 当前未经训练的“原生模型 6+2 步 + 双线性 latent 放大”路线，建立一条可验证、按生成后端隔离的 MiniMax H3 二采链路。新路线吸收 U09、U13、U16、U17 中已经实际使用的做法，同时保持 U11 只有一个工作流、用户只在导演台选择模式、无需手动连线。

最终必须同时满足：

- 不再把低分辨率 latent 用双线性或最近邻硬放大后冒充真实细节。
- FL 系列和 Reference 系列使用各自匹配的模型、LoRA、调度器和 sigma 路线。
- 只重建视频 latent；第一阶段生成的音频 latent 原样保留。
- 在生成开始前检查节点、模型、LoRA、RTX VSR 和可用显存；不允许任务运行到最后才报告依赖缺失。
- 2K、4K 表示唯一最终 MP4 的实际像素尺寸，同时在 UI、日志和元数据中公开 H3 首采尺寸、神经 latent 二采尺寸以及最终放大倍率。
- 不承诺 H3 原生 4K。4K 是在尽可能高的 H3 二采细节基准上逐帧 AI 重建得到的最终输出。

## 根因与参考工作流结论

### 当前 U11 的问题

当前 `quality_two_stage` 使用原生 H3 模型执行 8 步，将轨迹拆成 6+2；首采 `denoised_output` 通过 PyTorch 双线性插值放大约 1.5 倍，再以最后 2 个低 sigma 步继续采样。该路线没有训练型放大器，也没有 U16/U17 中与两个阶段匹配的 Turbo LoRA。结果是：

- 插值只能扩大 latent 网格，不能生成可信的高频细节；
- 2 个高分辨率尾步不足以修复屋檐、纹理和远景结构；
- 调高二采 denoise 或增加尾步又会带来灰屏、颗粒、内容漂移和显存峰值；
- RTX VSR 只能增强已经存在的边缘，无法补回首采阶段丢失的真实结构。

因此本次不再继续调当前 6+2 路线，而是替换架构。

### U09：保留 AV 处理方法，不采用整段图像空间往返

吸收以下能力：

- 第一阶段使用干净的 `denoised_output`；
- 使用 H3 AV 分离节点拆分视频和音频 latent；
- 只放大、重绘视频 latent；
- 第一阶段音频 latent 不缩放、不重新加噪，最后再合并；
- 第二阶段只运行低噪声区间。

不采用整段 `VAE 解码 -> 图像放大 -> VAE 重编码` 作为 U11 的默认二采。15 秒视频在该路径中会同时增加显存、系统内存、VAE 时间和颜色往返误差；此前 U11 的服务器测试已经出现崩溃、灰屏和极慢执行。

### U13：保留模式隔离和低显存思路，不复制重复图

吸收以下能力：

- 按 FL2VA、REF2VA 等后端选择对应的模型和加速资产；
- 4 步 Turbo、普通质量和低显存路线互相隔离；
- 缺少加速资产时不以错误低步数继续运行。

不复制 U13 的多套重复模式图，也不采用 `CreateVideo -> SaveVideo` 的整段全批次输出。U11 继续使用一个路由图和一个最终流式 MP4 输出节点。

### U16：Reference 路线

Reference 后端采用 U16 的核心组合：

- REF2VA 基础模型；
- `minimax_h3_ref2v_turbo_4step_v0.1_comfyui_bf16.safetensors`，默认强度 0.75；
- 8 步 sigma 轨迹，尾段使用 `H3SigmaRefiner` 增加 1 个低 sigma 步；
- `start_at_sigma=0.7`、`end_at_sigma=0`、`cosine`；
- 在第 4 步切分高、低 sigma；
- Euler 采样；
- 第一阶段干净视频 latent 进入训练型 3D latent 放大器；
- 第一阶段音频 latent 直接并回第二阶段。

该路线用于 `REF2VA`，也用于 I2VA、FL2VA、L2VA、T2VA 中选择 H3 原生 reference 音色的请求。Fish S2 不进入该路线。

### U17：FL 路线

FL 后端采用 U17 的核心组合：

- FL2VA 基础模型，不默认要求社区 hybrid 大模型；
- 第一阶段使用 `minimax_h3_fl2v_turbo_8step_v1.0_comfyui_bf16.safetensors`，默认强度 0.75；
- 第二阶段使用 `minimax_h3_fl2v_turbo_4step_v1.1_768p_comfyui_bf16.safetensors`，默认强度 0.70；
- `beta` 调度、8 步轨迹、Euler 采样；
- 在第 4 步切分为 4+4；
- 第一阶段输出使用 `denoised_output`；
- 分离 AV 后，仅将视频 latent 送入训练型 3D latent 放大器，默认 1.5 倍；
- 原音频 latent 直接合并到第二阶段；
- 第二阶段使用低 sigma 和第二套 768p LoRA。

该路线用于不依赖 H3 reference 后端的 T2VA、I2VA、FL2VA 和 L2VA。

## 架构与数据流

### 统一路由

导演台继续只公开一个“质量优先二采样”预设。后端根据生成模式和音色模式自动解析为：

1. `trained_latent_fl`：FL 模型、FL 两阶段 LoRA、beta/Euler、4+4。
2. `trained_latent_ref`：REF 模型、REF LoRA、H3SigmaRefiner、Euler、首采4步 + 尾段强化后的二采5步。
3. `bypass`：Fish S2、低显存长视频或不满足安全条件的组合不执行二采。

用户不能在 UI 中混选 FL LoRA、REF LoRA、调度器或二采后处理。API 收到不兼容组合时，在排队前返回中文参数错误。

### 两阶段流程

```text
导演台请求
  -> 模式/音色后端解析
  -> 依赖与显存前置检查
  -> 匹配的第一阶段模型补丁、LoRA、调度器和高 sigma
  -> 第一阶段采样
  -> 取 denoised_output
  -> 分离视频/音频 latent
  -> 训练型 H3 3D latent 放大视频（默认 1.5x）
  -> 原样保留音频 latent
  -> 合并 AV latent
  -> 匹配的第二阶段模型补丁、LoRA和低 sigma
  -> 第二阶段采样
  -> H3 VAE 解码视频与音频
  -> 可选的逐帧 RTX VSR
  -> 唯一最终 MP4
```

### 训练型 latent 放大依赖

U11 不复制许可证不明确的第三方实现源码，而是兼容调用已安装的外部节点：

- 新节点 ID：`MinimaxH3LatentUpscaler3D`
- 旧工作流兼容 ID：`MinimaxH3LatentUpscalerNode3D`
- 项目：<https://github.com/LBH-123-AI/Comfyui_Minimax_h3_latent_Upscaler>
- 模型目录：`ComfyUI/models/latent_upscale_models/`
- 默认模型：`minimax_h3_latent_upscaler_3d_bf16.safetensors`
- 模型地址：<https://huggingface.co/LBH-123-AI/Minimax_h3_latent_Upscaler/blob/main/minimax_h3_latent_upscaler_3d_bf16.safetensors>

调用层必须适配新、旧节点 ID，但只选择一个实际实现。节点或模型缺失时，导演台在 H3 采样前显示准确的安装地址和模型目录。

### 不叠加冲突加速器

二采路线不会照搬 U17 中同时出现的 SolAttn、PathchSageAttention、LowVRAMAttention、MemoryEfficientSage 和 ModelAttentionBackend。每次只选择一个已验证的 H3 注意力实现，再配合现有精确 attention/MLP 分块降低峰值。

EasyCache、RIFE 和 Fish S2 不进入训练型二采：

- EasyCache 可能改变两个阶段的缓存语义并软化运动细节；
- RIFE 会在动态云雾、建筑视差和高速运动中制造重影；
- Fish S2 是独立对白生成路线，不应与 H3 原生 AV latent 二采混合。

## 显存安全与2K/4K真实性

### 关键原则

训练型 latent 放大器节省的是获得更高分辨率 latent 的生成时间，不会消除第二阶段 H3 DiT 在目标网格上的显存峰值。因此必须按“第二阶段像素面积 × 帧数”限制任务，不能只看最终输出尺寸。

U11 在排队前计算并展示：

- H3 第一阶段尺寸和像素面积；
- 训练型 latent 二采尺寸和像素面积；
- 视频帧数；
- 当前 GPU 总显存和可用显存；
- 最终 RTX VSR 横纵放大倍率；
- 质量来源：`H3 原生`、`H3 神经 latent 二采`或`逐帧后处理重建`。

### 安全档位

安全档位是保守上限，不是显卡宣传上限：

| 可用显存 | 训练型二采策略 | 15秒策略 | 允许的最终目标 |
|---|---|---|---|
| 8–12GB | 默认不对长视频执行高分辨率第二采样；使用低显存单采和逐帧最终重建 | 二采旁路 | 最高1080p |
| 16–24GB | 仅在帧数和二采网格通过预算时开放，优先0.3–0.5MP首采后1.5x | 超预算时在开始前拒绝或改用低显存预设 | 最高2K |
| 28GB及以上 | 质量二采可使用约0.8–0.9MP首采，1.5x后约1.8–2.1MP细节基准 | 目标是可运行15秒二采 | 2K；4K通过逐帧RTX VSR输出 |

运行时还必须检查当前可用显存。其他任务或模型占用导致余量不足时，不能仅因显卡标称32GB就继续启动。安全预算必须保留模型加载、VAE、CUDA碎片和后处理余量。

### 2K与4K的定义

- 2K QHD：最终 MP4 必须由 `ffprobe` 验证为 2560×1440；高显存质量二采的神经 latent 细节基准目标约为 1888×1056 至 1920×1088，再由 RTX VSR 以约1.33–1.36倍输出。
- 4K UHD：最终 MP4 必须由 `ffprobe` 验证为 3840×2160；H3 不直接在4K latent上采样。高显存质量二采先获得约1080p的神经 latent 细节基准，再由 RTX VSR 逐帧2倍输出。
- 低显存档位不开放4K，避免把约512p来源以4倍以上线性倍率包装成“4K”。
- 请求的最终尺寸与二采尺寸相同时，RTX VSR自动旁路；目标更小时执行高质量缩小。

导演台的“最终尺寸”旁边必须显示类似：

```text
最终2560×1440；H3首采1280×704；神经latent二采1920×1056；RTX VSR约1.34x
```

从而避免仅凭容器像素尺寸把低清视频称为真正2K细节。

### 防止任务崩溃

前置检查按以下顺序执行：

1. 后端、模式、音色和性能预设兼容性。
2. 对应 FL/REF 模型是否存在。
3. 对应阶段 LoRA 是否存在且文件名匹配。
4. 训练型 latent 放大节点和模型是否存在。
5. sigma refiner 是否存在（Reference 路线）。
6. 最终选择 RTX VSR 时，驱动、SDK和 Python 依赖是否可创建真实效果。
7. 当前可用显存是否达到该帧数和二采网格的安全预算。

任何一步失败都在首采前终止，并给出中文安装或降档建议。不得静默改用错误 LoRA、错误 sigma、普通插值或伪 AI 放大。

二采开始前释放已经完成任务的编码器和无关模型；阶段切换只清理 CUDA 缓存和已经消费的张量，不把 H3 采样改为 CPU。最终 RTX VSR 开始前卸载 H3 采样模型，再在 GPU 上逐帧处理，避免 H3 与 VSR 同时常驻。

## UI与API

导演台保持现有视觉风格和宽度，只修改已有字段的可选项与说明：

- 性能预设仍显示“质量优先二采样”，内部根据后端选择 FL 或 REF 实现。
- 显示只读的“实际执行链路”“首采尺寸”“二采尺寸”“最终倍率”“显存安全结果”。
- 不增加需要用户连线的节点。
- 不暴露第三方节点的英文参数。
- 不兼容的性能模式不出现在当前模式的下拉框中。

API 在现有请求字段基础上返回以下解析结果：

- `resolved_two_stage_route`
- `first_stage_width`、`first_stage_height`
- `second_stage_width`、`second_stage_height`
- `final_width`、`final_height`
- `final_upscale_scale_x`、`final_upscale_scale_y`
- `vram_safety_tier`
- `quality_basis`
- `required_assets`

API 用户只提交生成模式、音色模式、性能预设、最终目标、时长和种子；LoRA、调度器、sigma 和放大节点由后端锁定。

## 错误处理与回退规则

- 缺少训练型放大依赖：拒绝“质量优先二采样”，提示安装；不回退双线性。
- FL/REF LoRA不匹配：拒绝任务；不带着低步数使用原生模型。
- 显存预算不足：在首采前给出安全的最高档位；不执行到二采阶段才 OOM。
- RTX VSR不可用：选择2K/4K AI重建时拒绝任务；选择原生输出时允许继续。
- 二采运行时发生无法提前预测的 CUDA OOM：停止任务、释放本次加载的模型并报告实际首采/二采网格和可用显存；不自动重复执行造成服务器连续崩溃。
- 非质量二采预设保持现有单采路线，不受新依赖影响。

## 测试与验收

### 自动测试

- 路由矩阵：FL模式、REF2VA、H3原生音色、Fish S2和低显存组合。
- LoRA契约：两个阶段的模型、LoRA、强度、调度器和采样器必须匹配。
- Sigma契约：FL为beta 8步4+4；Reference从8步轨迹的第4步切分，并由尾段强化新增1步，实际为4+5。
- AV契约：第二阶段音频 latent 与第一阶段音频 latent 内容、形状和时间轴保持一致。
- 放大契约：质量二采必须调用训练型3D latent放大器，不得调用双线性、双三次或最近邻作为质量路线。
- 显存预算：危险组合在首采前拒绝；安全组合返回实际三段尺寸。
- 输出契约：只保存一个MP4，目标尺寸、FPS、帧数、时长和音频流写入元数据。
- 工作流结构：单导演台、单采样路由、单最终输出、无节点重叠、无手动连线要求。

### 服务器实测矩阵

在以下测试完成前，不声明“已支持稳定2K/4K”：

1. RTX 3070 8GB：4秒和15秒低显存模式，最终1080p；确认不会进入高分辨率二采、不会OOM、MP4有声音。
2. 24GB显卡：4秒质量二采最终2K；确认二采生效、无灰屏、无颗粒爆发、无跳帧。
3. RTX 4080/5090 32GB：15秒质量二采最终2K；确认完整跑完且峰值不触发OOM。
4. RTX 5090 32GB：15秒质量二采最终4K；确认H3二采约1080p、RTX VSR逐帧2倍、不会建立整段4K GPU张量。
5. 每个文件使用 `ffprobe` 验证视频尺寸、编码、FPS、帧数、时长及AAC音频流。
6. 固定同一提示词和种子，对比当前问题视频，检查灰屏、噪点、远景结构、颗粒、重影、曝光和音频。

服务器日志必须包含：解析后端、两阶段LoRA、sigma数量和切分点、AV分离/合并、latent放大前后形状、显存检查结果、H3卸载、RTX VSR倍率以及最终 `ffprobe` 摘要。

## 实施边界

- 只维护一个 U11 工作流。
- 不启动用户本地 ComfyUI。
- 不默认下载或启用社区 hybrid 大模型。
- 不把第三方许可证不明确的实现复制进 Director Plus；使用显式依赖和前置检查。
- 不在同一路线叠加多个注意力后端。
- 先用自动测试验证路由与安全条件，再由用户在服务器完成2K/4K实测；没有日志和产物证据时不宣称问题修复。
